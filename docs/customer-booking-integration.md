# FE-14 · FE-20 고객 예약·문자 인증

- 출발점: 프론트 #24의 최신 수정본. 팀 승인 없이 병합하거나 배포하지 않는다.
- 일반 업체 링크: 접수 내용 확인 → 방문 주소 검색·선택과 저장 → 서버가 준 시간 선택 → 저장된 방문 연락처 인증 → 최종 확정.
- 본인 예약 조회는 별도 문자 인증(`RESERVATION_LOOKUP`)을 거친다. 상담 복구 인증(`INQUIRY_ACCESS`)과 섞지 않는다. 토큰은 URL과 브라우저 저장소에 남기지 않는다.
- 결과 유실 시 동일 요청 키로 재확인하고, 시간 충돌 시 후보를 다시 조회한다. 확정과 알림 발송 결과를 구분한다. 문자 발송 실패·인증번호 불일치·만료·한도는 화면 상태로 구분한다.

## 공유 Dev 반영 순서

1. 프론트 #24 승인·병합과 백엔드 #53(예약 확정·조회) 및 #48(고객 인증)의 Dev 반영을 확인한다. 백엔드 #49(주소 검색)의 실제 Dev 동작도 확인한다.
2. `CUSTOMER_BOOKING_ENABLED=true`는 예약·고객 인증 API를 검증할 테스트 환경에만 먼저 적용한다. 일반 접수·사진·시연 링크의 설정은 독립적이다.
3. `CUSTOMER_INQUIRY_RECOVERY_ENABLED`는 기본값 false를 유지한다. 백엔드가 번호 확인을 끝낸 문의만 목록과 토큰 발급 양쪽에서 허용하고, 비공개 테스트 업체에서 이를 확인한 뒤에만 켠다. UI 숨김 자체는 서버 접근을 차단하지 않는다.
4. 실제 문자 수신, 새 문의 주소 저장·후보·확정·조회, 다른 업체/번호 접근 차단, 예약 충돌·중복 요청을 팀 테스트 업체에서 확인한다. 인증번호·토큰은 증빙에 남기지 않는다.

로컬 검증은 `npm run check`, 운영 모드 빌드와 `tests/customer-live-booking.browser.mjs`를 사용한다. 브라우저 검사는 실제 고객 화면을 로컬 모의 API에 연결하며 문자나 외부 서비스를 호출하지 않는다. 로컬 서버는 35115 포트, 프론트 API 기준 주소는 `http://127.0.0.1:35116`으로 설정한다. 테스트에만 위 두 스위치와 `CUSTOMER_LIVE_ENABLED`를 켠다.

`tests/customer-booking-spring.browser.mjs`는 격리 Spring·PostgreSQL 통합 검증이다. 개발 프론트 35120, loopback Spring 35116, 전용 Docker 컨테이너 `ilro-wbs-nov19-api`·`ilro-wbs-nov19-db`와 로컬 테스트 문자 발송기로만 실행한다. 별도의 테스트 업체를 만들어 신규 접수 → 예약 저장 → 본인 예약 조회 → 번호를 인증한 상담만 복구를 확인한다. 공유 데이터베이스나 실제 문자 발송기에 연결하지 않는다.
